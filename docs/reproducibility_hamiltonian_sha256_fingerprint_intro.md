# 哈密顿量的 SHA-256「指纹」是什么？（写给第一次接触的同学）

本文用尽量直白的话解释：为什么在量子化学 / 量子计算工作流里，会给哈密顿量算一个 **SHA-256 指纹**，它和 **SCI 论文里说的「计算可复现」** 有什么关系，以及业界是不是常用这种做法。

---

## 1. 先用一句话说清楚

**指纹** = 把「这份哈密顿量（在计算机里长什么样）」按**固定规则**写成一段文本，再对这段文本做 **SHA-256 哈希**，得到一串**固定长度的十六进制字符**。  
**同一份算符、同一套规则 → 指纹相同；任一细节变了 → 指纹几乎一定变。**

你可以把它想成：**给整份算符办了一张「身份证号」**，用来对表、存档、查缓存，而不是把巨大的矩阵全文打印在论文里。

---

## 2. 为什么需要「指纹」，而不是直接比矩阵？

哈密顿量在程序里往往是一大堆 **Pauli 项**（例如 `X0 Z1`）和**系数**的组合。直接比较：

- 体积大，不方便写进论文或日志；
- 浮点数、排序顺序、内部表示若略有不同，容易误判「是否同一份对象」。

**指纹**解决的是：**用很短的一串字符，代表「规范化之后」的整份算符**。  
审稿人或未来的你自己只要对照：**配置 + 构造步骤 + 指纹**，就能判断「我们算的是不是同一份哈密顿量」。

---

## 3. SHA-256 到底是什么？（不要求你会密码学）

- **SHA-256** 是一种标准的**哈希函数**：输入任意长度的字节串，输出 **256 个二进制位**（通常写成 **64 个十六进制字符**，例如 `a3f2…`）。
- 特点（直观理解即可）：
  - **输入变一点点，输出看起来完全随机地变**（雪崩效应）；
  - 在工程意义上，**不同内容撞到相同输出（碰撞）的概率极低**；
  - **同样输入 → 同样输出**，与你在哪台电脑、哪天跑无关（只要输入字节完全一致）。

所以业界常用它做：**文件校验、镜像 digest、数据版本标识**等。

---

## 4. 在本仓库里，指纹具体怎么算？

实现见：`src/qchem_stack/chem/hamiltonian.py` 中的 `hamiltonian_fingerprint_from_qubit_operator`。

**思路分三步：**

1. **规范化（canonicalize）**  
   把 qubit 算符里的每一项拿出来，按**固定顺序**排序（例如按 Pauli 标签、再按系数参与排序），并把系数格式化成固定精度（代码里用 `:.16g` 这种科学计数/定点格式），避免「写法不同但数学相同」带来的歧义。

2. **拼成一段确定性的字符串**  
   例如把多项写成 `标签:系数;标签:系数;…` 这种**大家都约定好**的格式。只要算符相同且规则不变，这段字符串就**逐字符相同**。

3. **SHA-256**  
   把上面字符串用 UTF-8 编成字节，做 `SHA-256`，再取 **十六进制表示的前 32 个字符**（即 128 bit 前缀）作为对外展示的指纹。

> **小注**：严格说「完整 SHA-256」常指 **64 个 hex 字符**；这里用 **32 个字符前缀** 仍然是「基于 SHA-256 的指纹」，更短、好贴进表格；在科学工作流里很常见。若论文 Methods 要写精确，可写明「SHA-256 的十六进制前缀（前 32 字符）」。

同一套规则下：**相同 Pauli 展开与系数 → 相同指纹**；**映射不同、电子数不同、系数不同**等 → 指纹应不同（本仓库有对应测试，例如 `tests/chem/test_hamiltonian_fingerprint.py`）。

---

## 5. 指纹和「计算可复现」是什么关系？

**它能保证的：**

- 在**你们约定的构造链**上（从输入到最终 qubit 算符），若最终规范化表示一致，则 **指纹一致**；  
  指纹不一致，说明**至少有一处与预期不同**（很有用的**排错与审计**工具）。

**它单独不能保证的：**

- 数值库版本、BLAS 线程、随机数种子、模拟器后端、硬件噪声等，都会影响「同一次实验的数值轨迹」。  
  **指纹**主要钉住的是：**「我们声称的哈密顿量对象」是否一致**，这是 **SCI 语境里「计算可复现」的一块基础设施**（对象级 identity），常和 **配置哈希、协议哈希、种子、软件版本清单** 一起使用。

本仓库里还能看到与「可复现」相关的其它摘要，例如协议、`repro` 配置等处的 SHA-256 前缀，思路类似：**把关键对象变成可引用、可对比的短 ID**。

---

## 6. 这种做法在业界流行吗？谁在类似地用？

**非常流行。** 本质都是：**用内容哈希标识一份数据或制品**，而不是靠文件名或路径。

下面这些是「同一类思想」的代表性例子（不限量子）：

| 领域 | 常见用法 |
|------|----------|
| 容器 | Docker / OCI 镜像 **digest** 常用 SHA-256 |
| 版本控制 | Git 用哈希标识对象（历史上多为 SHA-1；生态在向更强摘要演进） |
| Python 生态 | 锁文件、可哈希依赖（如 pip 的 `--require-hashes`） |
| 数据与流水线 | DVC、Snakemake 等用哈希做缓存与溯源 |
| 学术存档 | Zenodo、期刊补充材料里常见的 **checksum**（SHA-256 很常见） |
| 可复现构建 | Reproducible Builds 等文档大量使用制品哈希 |

在 **量子化学 / 量子软件** 里，**每篇论文都在 Methods 里写「哈密顿量 SHA-256」** 还不算行业统一标准；但在**平台与工程实践**中，用哈希做 **缓存键、作业去重、日志审计** 非常普遍。把「哈密顿量指纹」**写进论文或公开复现包**，属于把工程上已经好用的做法，**显式提升为可发表的复现叙事**。

---

## 7. 你第一次接触时，建议记住的三句话

1. **指纹不是哈密顿量本身**，而是它的**短标识符**，由**规范化文本 + SHA-256** 得到。  
2. **指纹一致** ≈ 在你们的定义下，**这份 qubit 算符的规范化描述一致**（对象级一致）。  
3. **端到端可复现** 还要配合 **版本、种子、环境**；指纹是其中**清晰、可自动化检查**的一环。
