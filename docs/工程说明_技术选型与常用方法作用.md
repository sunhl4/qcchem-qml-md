## Pydantic：数据进来先做「质检」

### 一句话

**Pydantic 像一个有固定流程的质检员：**你把字典、JSON/YAML 解析结果交给模型，它立刻检查类型和约束是否合法；不对就报错，并尽量告诉你**是哪个字段、哪条规则**没过。

### 为什么值得用（不堆术语）

#### 1. 错误尽量暴露在「门口」

例如配置里写成 `n_electrons: "abc"`（本该是整数）。

- **不用结构化校验**：程序可能跑到很后面才崩，或默默算出怪结果（例如不合理的负数），排查成本高。
- **用 Pydantic**：在 `model_validate(...)` 或加载配置的那一刻就失败，并说明「该字段期望整数」。

#### 2. 少写散落的 `if … raise`

例如规则「活性电子数不能超过轨道数的两倍」。

- **手写**：在每个入口重复 `if`，容易漏、风格不一致。
- **Pydantic**：把规则集中在模型或校验辅助模块里（本仓库见 `src/qchem_stack/config/` 与各 `*_validation.py`），调用方只负责传入数据。

#### 3.  coercion 与单位转换可以「收口」

用户习惯用埃（Å）填坐标，而内部希望统一成玻尔半径（\(a_0\)）等。

- **手写**：在多个调用点乘系数，容易漏、难测。
- **Pydantic**：可在 validator / 自定义类型里**集中**做转换，下游代码只面对已规整好的值。（具体是否在本仓库某字段上启用，以对应模型为准。）

#### 4. 字典 → 可点号访问的对象

从 YAML/JSON 得到嵌套字典后，希望写成 `config.molecule` 而不是一串 `["molecule"]`。

- **手写**：层层拆键、手动建类或 `NamedTuple`，漏键往往在运行中才暴露。
- **Pydantic**：`ExperimentConfig.model_validate(data)` 一次建成嵌套结构；字段名拼错会在校验阶段提示，而不是深算到一半才 `KeyError`。

#### 5. 报错带「路径」，定位更快

校验失败时常见 `active_space.n_electrons` 这类路径。

- **模糊报错**：只知道「有个值不对」，要猜层级。
- **Pydantic**：错误信息通常能指向**嵌套位置**，和配置文件结构更容易对照。

#### 6. 编辑器友好，少写错字符串键

`config.quantum` 这类属性可被 IDE 补全；相比 `config["quantum"]`，少拼一个字母就少一类后期才发现的 bug。

### 生活类比

填一份复杂报名表（姓名、年龄、证件号、家庭成员……）。

- **手工收表**：每个格子都要人肉核对，漏一项后面统计就可能全乱。
- **Pydantic 类似自动机**：表一进去就按规则扫描——「第 3 行年龄不是数字」「第 5 行证件号位数不对」。规则变更时，只改「机器设定」（模型与校验），而不是教会每个人一套新检查方式。

### 三句话小结

- **数据一进模型就验身份**，减少「带病数据」流进计算流水线。
- **报错尽量说清字段与原因**，缩短从现象到根因的时间。
- **代码更扁平**：用属性访问代替大量嵌套字典与重复校验。

### 在本仓库里怎么用

实验与量子相关配置集中在 `src/qchem_stack/config/`，校验分层（哪些放 `Field`、哪些放 `*_validation.py`）见 [config_校验分层约定.md](config_校验分层约定.md)。

## 根包 `__init__.py`：轻量门面，不堆业务 API

### 一句话

**`src/qchem_stack/__init__.py` 只做「整库都可能用到、且不该拖慢导入」的横切出口**；配置、流水线、化学、量子等真正干活的 API 留在各自子包的 `__init__.py` 里，按领域导入。

### 为什么这样设计（不堆术语）

#### 1. `import qchem_stack` 要轻

若在根 `__init__.py` 里再导出 `ExperimentConfig`、`run_pipeline_sync` 等，会连锁拉起 `config`、`orchestration`、`chem` 等子树（含大量 NumPy、可选 PySCF 路径）。  
根包当前只 re-export **异常**、**严格 JSON 导出两个小函数** 和 **`__version__`**，避免「只想看版本号却 import 了半座化学库」。

#### 2. 公开 API 按子包分菜单

| 你想做的事 | 推荐导入方式 |
|------------|----------------|
| 读/写实验 YAML、建 `ExperimentConfig` | `from qchem_stack.config import …` |
| 跑整条流水线 | `from qchem_stack.orchestration.pipeline import run_pipeline_sync` 等 |
| 经典/嵌入/积分 | `from qchem_stack.chem import …` |
| 量子算法与后端 | `from qchem_stack.quantum import …` |
| 按失败类型捕获或打日志 | `from qchem_stack import PipelineError` 或 `from qchem_stack.exceptions import …` |
| 结果落盘 / API 用严格 JSON | `from qchem_stack import repro_json_dumps` 或 `from qchem_stack.repro import …` |

子包文档与 `__all__` 才是各领域的「官方菜单」；根包不是总目录。

#### 3. 根上 re-export 的是「横切」能力

- **异常**（`QChemStackError` 及其子类）：给集成方、HTTP API、运维脚本在**包边界**按失败种类分支，而不是满仓库抓 `ValueError`。定义见 `src/qchem_stack/exceptions.py`；根包只暴露常用子集（例如 `PreQuantumCapabilityError` 仍在 `exceptions` 子模块，未放进根 `__all__`）。
- **`repro_json_dumps` / `repro_dict_for_strict_json`**：流水线、测试、对外接口多处要把结果做成可审计、可 diff 的 JSON；与 `qchem_stack.repro` 子包导出的是同一对函数，根上再暴露一次便于 `from qchem_stack import …`。
- **`__version__`**：从已安装 distribution 名 `qchem-stack`（与 `pyproject.toml` 的 `[project] name` 一致）读取；未 `pip install` 时回退为 `0.1.0`。

#### 4. 和 Pydantic 校验的分工

- **字段值、类型、模型内交叉约束**：`pydantic.ValidationError`（在 `ExperimentConfig.model_validate` / `from_yaml_dict` 时抛出）。
- **文件 I/O、YAML 根不是 mapping、几何文件缺失、配置辅助逻辑发现的依赖缺口**：`ConfigurationError`（可在根包或 `qchem_stack.exceptions` 导入）。

配置**模型**归 `config` 子包；**异常类型**作为跨子系统契约，才在根包露面。

### 生活类比

商场总服务台只办三件事：查营业时间（版本）、按投诉类型指路（异常分类）、统一开发票格式（repro JSON）。  
具体买衣服、吃饭、看电影要去各楼层专柜（`config`、`orchestration`、`chem`…），不会把所有专柜货架都堆在大门口。

### 三句话小结

- **根包 = 薄门面**：版本 + 少数横切工具 + 常用异常，不承载业务主 API。
- **子包 = 厚菜单**：各领域 `__all__` 与文档说明从哪 import。
- **内部代码**多数仍写 `from qchem_stack.config import …`；根上的 re-export 主要方便**外部集成**与 `except qchem_stack.PipelineError` 这类写法。

### 在本仓库里怎么用

实现见 `src/qchem_stack/__init__.py`。对照阅读：`src/qchem_stack/config/__init__.py`（配置公开面）、`src/qchem_stack/repro/__init__.py`（可复现导出）。异常体系见下一节。

## `exceptions.py`：按「失败阶段」分类的库内错误

### 一句话

**`src/qchem_stack/exceptions.py` 定义本库对外可识别的异常类型**：在包边界用「种类」区分失败，方便集成方、HTTP API、测试和日志按阶段处理；**不**用这一文件替代 Pydantic 的字段校验，也**尽量不用**裸 `ValueError` / `RuntimeError` 表示「用户/配置/流水线」层面的可预期失败。

### 为什么单独一个文件（不堆术语）

#### 1. 调用方需要知道「该不该重试 / 改配置 / 换后端」

同一种 `RuntimeError("something failed")` 无法区分：是 YAML 写错了、嵌入没收敛，还是当前 backend 不支持某能力。  
固定异常类型 + 稳定 `str(exc)` 文案，让 `except ConfigurationError`、`pytest.raises(PipelineError, match=...)`、API 统一返回 422 成为可能。

#### 2. 模块极轻，任意子包都能安全 import

`exceptions.py` **只继承标准库 `Exception`**，不 import `config`、`chem`、`numpy`。因此 `config/io.py`、`chem/embedding/…`、`api/app.py` 都可以 `from qchem_stack.exceptions import …`，而不会形成「为了报错先拉起半条流水线」的循环依赖。

#### 3. 与 Pydantic 分工明确（和根包章节一致）

| 场景 | 抛什么 | 典型入口 |
|------|--------|----------|
| 字段类型错、单字段约束、模型内交叉规则 | `pydantic.ValidationError` | `ExperimentConfig.model_validate` / `from_yaml_dict` |
| 配置文件找不到、YAML 根不是 dict、几何文件路径、配置辅助函数里的跨模块策略规则 | `ConfigurationError` | `config/io.py`、`config/_experiment_validation.py`、`config/geometry_files.py` 等 |
| 配置已通过，经典/编排/变分/离线包等执行失败 | `PipelineError` | `orchestration/*_stage.py`、`chem/pre_quantum_*.py`、`quantum/variational_plugins/*` 等 |
| 分片 / 浴 / Schmidt 嵌入构造或自洽失败 | `EmbeddingError` | `chem/embedding/projection_hamiltonian.py`、`schmidt_production.py` 等 |
| 结果字典无法按严格规则 JSON 化 | `ReproExportError` | `repro/export.py` |
| 所选 backend / 注册表无法满足某 pre-quantum 能力 | `PreQuantumCapabilityError` | `chem/pre_quantum_builder_registry.py`、`chem/integrals/exporter_registry.py` |

新增配置字段时仍以 Pydantic + `_xxx_validation.py` 为主，见 [config_校验分层约定.md](config_校验分层约定.md)。

### 类层次与各子类意图

```text
Exception
└── QChemStackError          # 本库「有意对外暴露」的错误基类
    ├── ConfigurationError   # 配置加载 / 非 Pydantic 的配置策略校验
    ├── ReproExportError     # repro / 运行结果严格 JSON 导出
    ├── PipelineError        # 编排与计算阶段（配置已合法）
    ├── EmbeddingError       # 嵌入子流程
    └── PreQuantumError      # pre-quantum 契约/构建（基类，便于以后扩展）
        └── PreQuantumCapabilityError  # 能力/后端不满足
```

| 类 | 意图（何时 raise） | 根包 `__all__` 是否 re-export |
|----|-------------------|------------------------------|
| `QChemStackError` | 捕获「任意本库业务异常」的总闸，例如 HTTP 层 `except QChemStackError` | 是 |
| `ConfigurationError` | 实验 YAML I/O、根结构、几何文件、`_experiment_validation` 等**不走 Pydantic 字段路径**的规则 | 是 |
| `ReproExportError` | repro 含环、非有限浮点、不支持的类型等 | 是 |
| `PipelineError` | SCF/CAS、pre-quantum 构建、precomputed manifest、变分插件、阶段执行等**流水线内**失败 | 是 |
| `EmbeddingError` | 活性空间与 MO 维度、冻结轨道掩码、Schmidt 等**嵌入几何/代数**不一致 | 是 |
| `PreQuantumError` | 预留的 pre-quantum 失败基类；当前仓库内**无直接 `raise PreQuantumError`** | 否 |
| `PreQuantumCapabilityError` | builder / integral exporter 注册表发现「要的能力 backend 没有」 | 否（从 `qchem_stack.exceptions` 导入） |

消息字符串应**稳定、可测**：测试里常用 `pytest.raises(..., match="…")`；改动文案视为破坏性变更。

### 生活类比

医院分诊：挂号处（配置 / `ConfigurationError`）、化验科（嵌入 / `EmbeddingError`）、手术室（流水线 / `PipelineError`）、档案室复印（导出 / `ReproExportError`）、设备科（缺仪器 / `PreQuantumCapabilityError`）。  
病人卡片上都印同一套「本院病历号」（`QChemStackError`），前台可以统一接待，再按科室转。

### 三句话小结

- **一个文件、一棵树**：轻量、无重依赖，全库共用的错误「词汇表」。
- **按失败阶段选子类**，与 `ValidationError` 并列而非替代。
- **集成边界**用 `QChemStackError` 兜底（如 `api/app.py` 同步跑流水线 → HTTP 422），细分类在业务与测试里使用。

### 在本仓库里怎么用

- **定义**：`src/qchem_stack/exceptions.py`（模块 docstring 即设计意图）。
- **抛出**：在对应领域模块 `raise XxxError("…")`，必要时 `from exc` 链保留原因。
- **捕获**：测试与子模块 `from qchem_stack.exceptions import PipelineError`；对外脚本可用 `from qchem_stack import PipelineError`（根包 re-export）。
- **HTTP**：`src/qchem_stack/api/app.py` 在同步 `run_pipeline_sync` 外捕获 `QChemStackError`，映射为 422；Pydantic 请求体校验仍由 FastAPI 处理 `ValidationError`。
- **不要**：把普通编程 bug（索引越界、断言）随便改成 `PipelineError`；仅用于**可预期、可向用户/运维说明**的失败。
